# Mistakery — Reigns-like Design Audit Rubric

Версия: research draft, 12 июля 2026.

Назначение: единообразно проверять карточку, выбор, сюжетную цепочку, колоду, ресурсы и полный run. Рубрика основана на `MISTAKERY_REIGNS_RESEARCH.md`, но содержит и проектные решения Mistakery.

## 1. Система оценки

Каждый применимый критерий получает:

- **2 — PASS:** критерий выполнен и подтверждён текстом, данными или playtest.
- **1 — WARNING:** решение работает, но имеет заметный риск или недостаточно доказательств.
- **0 — FAIL:** критерий нарушен.
- **N/A:** критерий неприменим; не входит в знаменатель.

Процент категории:

`набранные баллы / максимум применимых баллов × 100`

Интерпретация:

- **90–100%:** готово к внешнему playtest.
- **75–89%:** внутренний прототип; нужны точечные исправления.
- **60–74%:** структура нестабильна; copy polish преждевременен.
- **ниже 60%:** требуется переработка концепции или системы.

## 2. Hard gates

Независимо от общей оценки материал не готов к внешнему тесту, если присутствует хотя бы один пункт:

- карточка противоречит State Bible;
- упоминается несуществующий user, customer, character или organization;
- непонятно, кто совершил действие и чего хочет;
- оба ответа являются одним и тем же действием;
- решение игрока отменяется немотивированным `too late`;
- effect не имеет причинной связи с действием;
- обязательная карта недостижима;
- возникает dead end без ending;
- full-run build заканчивается техническим preview вместо согласованной развязки (не применять к явно обозначенному onboarding test build);
- одна и та же pressure card повторяется в коротком run;
- две pressure cards идут подряд без отдельного режима;
- paid outcome выдаётся без реальной оплаты;
- текст не помещается в четыре визуальные строки на целевом экране;
- игрок не способен после первых пяти решений объяснить продукт, роль и цель.

## 3. Audit одной карточки

### 3.1. State integrity

- [ ] Все упомянутые сущности существуют на данном ходу.
- [ ] Стадия prospect / lead / customer / user названа корректно.
- [ ] Каждое число имеет однозначный объект и владельца.
- [ ] Местоимения `we`, `us`, `they`, `them` имеют один очевидный референт.
- [ ] Отправитель может логично знать сообщаемую информацию.

### 3.2. Messenger causality

- [ ] Понятно, почему сообщение пришло именно сейчас.
- [ ] Отправитель сообщает действие, результат, просьбу, угрозу или последствие.
- [ ] Сообщение не объясняет фаундеру общеизвестное ради аудитории.
- [ ] Карта связана с предыдущим состоянием или является допустимым ambient event.
- [ ] Срочность сообщения соответствует допустимой задержке следующего beat.

### 3.3. Information density

- [ ] За три секунды понятно, кто что сделал или собирается сделать.
- [ ] Понятно, чего отправитель хочет от игрока.
- [ ] Есть достаточно информации для рискованного выбора.
- [ ] Необходимый смысл не принесён в жертву длине.
- [ ] Текст укладывается максимум в четыре визуальные строки.

### 3.4. Character

- [ ] Действие соответствует роли персонажа.
- [ ] Голос можно узнать без handle.
- [ ] Bold trait порождает действие, а не только catchphrase.
- [ ] Персонаж не повторяет свою предыдущую шутку другим словами.
- [ ] Второй голос не спрятан в пересказе или длинной цитате.

### 3.5. Humor

- [ ] В основе находится узнаваемая startup pain.
- [ ] Персонаж воспринимает её как нормальную.
- [ ] Эскалация конкретна и визуализируема.
- [ ] Мат не является единственным панчлайном.
- [ ] Шутка не требует расшифровки до понимания действия.

**Card readiness:** минимум 80%, без hard gate. Для первых пяти карт — минимум 90%.

## 4. Audit пары ответов

### 4.1. Action clarity

- [ ] Обе кнопки описывают действие игрока.
- [ ] Каждая укладывается в 1–3 слова или имеет обоснованное исключение.
- [ ] Игрок понимает принципиальную разницу между действиями.
- [ ] Следующая карта не отменяет выбранное действие.

### 4.2. Decision space

- [ ] Нет очевидной пары `разумно / идиотски` без контекстного соблазна.
- [ ] Каждый ответ выражает стратегию, ценность или допустимый риск.
- [ ] Цена каждого варианта релевантна текущему состоянию.
- [ ] Выбор способен вызвать короткую паузу и сомнение.
- [ ] Один ответ не доминирует другой во всех ресурсных состояниях.

### 4.3. Consequence legibility

- [ ] Затронутые шкалы логично следуют из действия.
- [ ] Направление можно приблизительно предположить из ситуации.
- [ ] Неожиданное последствие является callback или характерным действием, а не произволом.
- [ ] `effect_reason` объясняет каждый ненулевой эффект.
- [ ] Реальная оплата, financing или saving — единственные источники роста Cash.
- [ ] Внутреннее действие не меняет Customers без внешнего сигнала.

### 4.4. Structural distinction

- [ ] Ответы отличаются effects, flags, eligibility, weight, follow-up или ending.
- [ ] Одинаковый immediate `next` компенсирован различимым будущим state.
- [ ] Если оба ответа сходятся, решение оставляет хотя бы одно проверяемое последствие.
- [ ] Панические и маниакальные labels сохраняют то же действие.

**Choice readiness:** минимум 80%, без фиктивного выбора.

## 5. Audit ресурса

Для каждого из Cash, Team, Customers и Founder:

- [ ] Ресурс представляет отдельную форму власти или риска.
- [ ] Игрок может объяснить его обычным языком.
- [ ] Низкая граница имеет тематически точный crisis.
- [ ] Высокая граница имеет тематически точный crisis.
- [ ] Верхний crisis выражает избыток силы, а не случайное наказание.
- [ ] Карты низкого диапазона логично отличаются от обычных.
- [ ] Карты высокого диапазона логично отличаются от обычных.
- [ ] Ресурс влияет на eligibility или writing, а не только на death check.
- [ ] Эффекты распределены по колоде без постоянного доминирования одной шкалы.
- [ ] Игрок может понять причину поражения без точных чисел.

**Resource readiness:** минимум 80% по каждому ресурсу; обе границы обязательны.

## 6. Audit карты в global state

- [ ] Определены условия, при которых карта допустима.
- [ ] Определены состояния, при которых карта невозможна.
- [ ] Определён вес относительно обычных карт.
- [ ] Определено, может ли карта повторяться в run.
- [ ] Определён cooldown или recency rule.
- [ ] Указано, относится ли она к active arc.
- [ ] Указано, является ли она forced, weighted или ambient.
- [ ] Указано, какие qualities создаёт каждый ответ.
- [ ] Указано, какие будущие cards открываются или усиливаются.
- [ ] Указано, какие cards становятся нелогичными и закрываются.

Если карточка не имеет этих полей в JSON, ответы должны быть воспроизводимо вычислимы из схемы.

## 7. Audit сюжетной арки

### 7.1. Causal spine

- [ ] Есть ясное запускающее событие.
- [ ] Каждый обязательный beat следует из предыдущего.
- [ ] Buyer или antagonist представлен до требования решения.
- [ ] Роли персонажей не подменяются ради связки.
- [ ] Финал является следствием решения игрока, а не таймера.

### 7.2. Modularity

- [ ] Определены обязательные causal pairs.
- [ ] Определены beats, которые можно отложить.
- [ ] Определены допустимые ambient interruptions.
- [ ] Active arc меняет weights или eligibility.
- [ ] Арка не является целиком одной forced очередью без необходимости.

### 7.3. Memory

- [ ] Минимум одно решение возвращается callback позднее.
- [ ] Callback происходит после достаточной, но не разрушающей смысл задержки.
- [ ] Callback сохраняет точный смысл первоначального действия.
- [ ] Персонаж помнит выбор игрока.
- [ ] Финал различает ключевые стратегии прохождения.

### 7.4. Variation

- [ ] Существует минимум два содержательно разных пути.
- [ ] Разные пути меняют не только числа, но и события.
- [ ] Отказ действительно отменяет или переключает событие.
- [ ] Повторный run может создать другое сочетание моментов.
- [ ] Обязательная причинность не зависит от случайного выпадения редкой карты.

**Arc readiness:** минимум 80%; causal spine и финал должны получить 100%.

## 8. Audit deck scheduler

### 8.1. Eligibility

- [ ] Перед каждым выбором формируется единый список допустимых карт.
- [ ] Несовместимые с world state карты исключаются.
- [ ] Недавно показанные карты исключаются или резко понижаются в весе.
- [ ] Dead characters и завершённые события не возвращаются.
- [ ] Карты не ссылаются на ещё не произошедшие события.

### 8.2. Weighting

- [ ] Active arc повышает вероятность связанных cards.
- [ ] Опасный ресурс повышает вероятность тематических реакций.
- [ ] Срочный callback имеет приоритет над ambient card.
- [ ] Вес не используется как замена обязательной причинности.
- [ ] При пустом pool существует безопасное, логичное поведение без повтора использованной карты.

### 8.3. Mode control

- [ ] Forced sequence используется только для непосредственных последствий или отдельного режима.
- [ ] После локальной подсистемы игра возвращается в общий pool.
- [ ] Ambient cards не идут подряд без сознательной причины.
- [ ] Игрок не видит техническую границу между story и pressure card.
- [ ] Randomness создаёт вариативность, а не semantic incoherence.

### 8.4. Current Mistakery test-slice note

Это не FAIL текущего onboarding test build и не вывод о целевой архитектуре:

- `activeArc` записывается, но не участвует в selection внутри onboarding test;
- weighted pool применяется только к pressure cards;
- тесты закрепляют остановку после шестого onboarding decision;
- story arcs существуют в JSON, но намеренно не входят в этот onboarding test.

Проверять эти пункты как FAIL можно только после того, как команда снова включит полный run.

**Scheduler readiness:** минимум 85%; eligibility и empty-pool behavior — 100%.

## 9. Audit pressure / ambient card

- [ ] Событие допустимо в текущем world state.
- [ ] Оно не требует несуществующего user, customer или public feature.
- [ ] Оно отражает уже существующую startup pressure.
- [ ] У него есть собственный маленький trade-off.
- [ ] Оно не повторяет структуру предыдущей pressure card.
- [ ] Оно не разрывает срочный causal pair.
- [ ] Оно не выглядит как отдельный comedy sketch из другой игры.
- [ ] Оно создаёт quality, callback или ресурсный риск, а не только заполняет ход.
- [ ] После него история возвращается естественно, без ощущения очереди.
- [ ] В одном run карта не повторяется дословно.

**Ambient readiness:** минимум 80%; state validity — обязательна.

## 10. Audit crisis и ending

- [ ] Ending называет конкретную потерю власти или чрезмерную силу.
- [ ] Текст связан с ресурсом, который достиг границы.
- [ ] Верхний и нижний ending отличаются не только направлением числа.
- [ ] Ending отражает недавние решения или active qualities.
- [ ] Поражение понятно без показа точного delta.
- [ ] Смерть или крах являются запоминающейся сценой.
- [ ] Победа требует фактического paid invoice или paid pilot.
- [ ] Бесплатное событие не маркируется коммерческой победой.
- [ ] Crisis имеет приоритет над победой, если ресурс уже вышел из коридора.
- [ ] Rescue не стирает смысл накопившейся проблемы.

**Ending readiness:** минимум 85%; causal explanation и payment truth — 100%.

## 11. Audit полного run

### 11.1. Player mental model

После первых пяти решений новый игрок может объяснить:

- [ ] кто он;
- [ ] что строит;
- [ ] кому продаёт;
- [ ] чего пока нет;
- [ ] что означают четыре ресурса;
- [ ] что является целью;
- [ ] почему возникло текущее событие.

### 11.2. Dramatic curve

- [ ] Вступление создаёт проблему, а не только tutorial.
- [ ] Давление постепенно растёт.
- [ ] Появляется конкретная возможность оплаты.
- [ ] Выборы усложняют мир, а не только уменьшают шкалы.
- [ ] Финал разрешает центральную коммерческую проблему.

### 11.3. Variety

- [ ] Нет дословных повторов внутри run.
- [ ] Нет двух последовательных ambient interruptions.
- [ ] Голоса персонажей чередуются осмысленно.
- [ ] Повторный run создаёт другую последовательность или callbacks.
- [ ] Игрок встречает смесь authored и less-authored moments.

### 11.4. Fairness

- [ ] Игрок понимает, почему проиграл.
- [ ] Случайность влияет на ситуацию, но не отменяет стратегию.
- [ ] Ни одна скрытая карта не делает поражение неизбежным без сигнала.
- [ ] Обе границы ресурсов достижимы, но не доминируют случайно.
- [ ] Победный путь существует для каждой основной арки.

### 11.5. Experience

- [ ] Обе кнопки всегда видны.
- [ ] Сообщения читаются без прокрутки.
- [ ] Темп можно выбирать самостоятельно.
- [ ] Ресурсный preview понятен.
- [ ] Restart полностью сбрасывает run state.

**Run readiness:** минимум 85%, mental model — 100%.

## 12. Автоматизируемые проверки

Будущий `audit-deck` script должен проверять:

- unique IDs;
- missing `next`, endings, crises и sources;
- reachability;
- dead ends и cycles;
- unused flags;
- impossible requires/excludes;
- одинаковые left/right labels;
- идентичные effects и state changes;
- одинаковый `next` без различимого persistent consequence;
- cards без `effect_reason`;
- growth Cash без payment/funding/saving reason;
- internal action с изменением Customers;
- repeat eligibility;
- sequential pressure cards;
- callback delay;
- source frequency;
- resource effect distribution;
- отсутствующие high/low crises;
- story cards, недоступные scheduler в build, объявленном полным run;
- visible line count;
- repeated n-grams и конструкции `too late`;
- run length и outcome distribution через seeded simulations.

Автоматический PASS не заменяет human narrative audit.

## 13. Обязательный human playtest

После каждого значимого изменения провести минимум три ручных прохода:

1. **Naive:** выбирать по буквальному смыслу кнопки.
2. **Resource optimizer:** выбирать по текущему риску шкал.
3. **Character role-play:** действовать как определённый тип фаундера.

После каждого хода записывать:

- что, по мнению игрока, произошло;
- что он ожидает от обеих кнопок;
- какие шкалы, по его мнению, затронутся;
- почему появилась следующая карта;
- считает ли он её callback или случайной вставкой.

Любое систематическое расхождение между ожиданием и фактом требует исправления текста, state model или scheduler.

## 14. Definition of Done для skill

Будущий skill можно считать пригодным только если он без подсказки обнаруживает в текущем проекте:

- искусственную экспозицию;
- semantic ambiguity prospects / leads / users / customers;
- несуществующих сущностей;
- фиктивные или доминирующие ответы;
- однообразные `same next` без persistent consequence;
- линейную природу story arcs;
- отделённый pressure-only weighted pool;
- неиспользование `activeArc` в общем scheduler;
- ошибочную остановку полного run после onboarding (не применять к специально изолированному onboarding test);
- ресурсные эффекты без внешней причины;
- повторяющиеся комедийные паттерны;
- слабые или произвольные high-bound crises.

Если skill перечисляет только длину текста, два ответа и наличие четырёх ресурсов, он не понимает дизайн Reigns достаточно глубоко.
